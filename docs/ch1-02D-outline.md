## 开头

**Takeaway：02A-02C 建立了 principle，但 principle 本身不能直接拿来干活。你需要把它们落地成文档结构和工作流。**

Motivation：读者看完 02A-02C 知道了分层、维度、交叉验证、迭代循环。但坐下来面对一个真实项目，第一个问题是：这些概念具体落地成什么？文件怎么组织？模板长什么样？流程怎么串？

这一节用两个东西来回答。一个是社区成员开发的 AILock-Step Feature Workflow，展示 principle 怎么变成工具设计。另一个是在 RuoYi-Vue 项目上跑通的 OKR 系统需求，展示工具实际运行时产出了什么。

前者是空壳（结构和流程），后者是填充（真实内容和迭代记录）。

## Part 2：一个需求的完整 Walkthrough（OKR 系统）

**Part Takeaway：一句话需求经过结构化展开和两轮迭代修正，变成了一份覆盖三个维度的可执行 spec。这个过程中人实际做的只有一件事：在每轮 review 后做产品决策。**

### 输入：一句话

- 需求："实现一个OKR系统，支持按季度配置每个员工的O和KR"
- 项目：RuoYi-Vue（Spring Boot + Vue 2 企业开发框架），就是 Part 1 展示 project-context.md 的那个项目
- 先交代结果（总分）：这句话最终变成了 7 section 的产品规格书，经过 2 轮 review 和 9 个产品决策。

### Agent 展开：三个维度怎么从一句话里长出来

**Takeaway：Agent 从一句话中推导出了 50 倍的信息量，但每一条新增信息都在回答一个如果不回答就会产生歧义的问题。**

意图维度：
- Agent 识别出 3 个 feature（目标管理、关键结果管理、季度总览），每个有独立的 user story
- 生成了术语表，锁定了"目标""关键结果""完成率""季度"的精确定义
- 展示目标管理的 user story 原文

验收维度：
- 每个 feature 有 4-5 条 acceptance criteria（可检查的条件）
- 用户流程描述了完整的操作步骤序列（从点击"新增"到创建完成）
- 业务规则用编号表格列出（BR-001 级联删除、BR-002 KR 数量限制、BR-003 完成率范围...）

约束维度：
- API Contract 表界定了前后端的边界（每个端点的 URL、方法、参数、响应格式）
- Out of Scope 列了 8 项明确排除的功能，每项标注排除理由
- Key Rules 在每个 feature 内部定义了业务约束（KR 最多 5 个、标题最长 200 字符等）

### 迭代：两轮 review 暴露了什么

**Takeaway：第一版 spec 有 5 个问题。每个问题如果不在 spec 阶段解决，就会在代码阶段由 Agent 自己做决定。在 spec 阶段改一行文字的成本，远低于在代码阶段改几十行加重新测试。**

第一轮（5 个问题）：
- Critical：API 端点完全没定义。展开讲：如果不定义会怎样？Agent 自己编 API 路径和参数格式，前后端对不上。决策：添加 API 表，只列 URL 和方法，遵循 RuoYi 标准。
- Major：KR 管理是展开行还是详情页？展开讲：两种选择的 tradeoff。决策：展开行（最小复杂度）。
- Major：状态字段有没有状态机？决策：自由编辑（最小复杂度）。

第二轮（4 个问题）：
- "员工"跟 sys_user 的关系、"新增KR"按钮位置等
- 问题的严重度在下降（第一轮有 Critical，第二轮没有），说明在收敛

关键观察：9 个决策中的每一个都有明确的决策原则（最小复杂度 > Demo 可演示性 > 原始意图 > 一致性）。这些原则是 project-context 层面的约束，在每个具体决策中被应用。

### 从 spec 到实现（简短）

**Takeaway：收敛的 spec 直接驱动了代码生成和合规检查。测试的细节留给下一章。**

- Spec 收敛后，Agent 生成了 2 张表、12 个后端文件、4 个前端文件、1 个 SQL
- 合规检查逐项对照 spec：13 条 AC 全部通过，5 条业务规则全部通过
- 合规检查发现了几个"spec 写对了但代码没跟上"的问题（默认值、校验缺失），修复后通过
- E2E 测试 7/7 通过。测试怎么设计、怎么防止 Agent 自己出题自己答，下一章展开。

### 人在这个过程中做了什么

**Takeaway：人的投入集中在 spec review 阶段的产品决策。后面的实现和验证基本不需要介入。**

- 不单独成节，融入 walkthrough 的叙事中
- 在 OKR 案例里，人做的事情是：看 Agent 生成的 spec 草稿，在两轮 review 中对 9 个问题做产品决策
- 后面的代码生成、合规检查、E2E 测试，人没有介入
- 这就是 02C 讲的"人是意图的唯一裁判"的实际体现

## 本章小结

**Takeaway：规约的本质是意图对齐。从一句话到可执行 spec 的完整链路，就是前面所有 principle 合在一起的实际运行。**

回扣全章 takeaway：
- 信息分层 → CLAUDE.md / project-context / feature docs
- 三个维度 → spec 模板的意图/验收/约束字段
- 迭代循环 → 两轮 review + 9 个决策 → 收敛
- 交叉验证 → 合规检查逐项对照 spec
- 人的角色 → 产品决策（意图对齐），其余交给 Agent

承上启下：规约解决了"做什么"。但这个案例里的合规检查发现了几个 spec 写对了但代码没跟上的问题。怎么系统化地验证 Agent 的产出是否跟 spec 一致，下一章展开。
