# 引言：从 Vibe Coding 到 Harness Engineering（内容 Outline）

> 本文件是写作大纲，不是最终章节。每段标注了在论证中的位置和要传达的具体内容。

**Chapter takeaway: Vibe coding 在结构上不可行。Agent 的结构性特征决定了你需要闭环控制体系，不是更好的 prompt。**

## Vibe Coding 碰壁

**Section takeaway: 墙是结构性的。模型在变强，天花板在升高，但天花板还在。**

**开局体验。** 打开 Agent，自然语言说需求，几分钟出代码，改两轮能用。你开始交给它越来越多的任务，一个下午搞定过去两天的活。

**碰壁。** 不是一下子碰到的，是慢慢感觉到的。项目大了，改一个功能坏另一个，修 bug 引入新 bug。来回改四五轮，效率反而不如自己写。

**天花板在升高，但天花板还在。** 过去两年模型能力在持续提升，从 GPT-4 到 Claude 3.5 Sonnet 到 Opus 4.6，每一代都更强，你确实感受到了进步：能 handle 的项目更大了，产出质量在提升。你自己也在进步：prompt 写得更精确了，给的上下文更有针对性了。但每过一阵子，同样的崩溃模式又出现了。项目再大一点、迭代再多几轮，又是改一个坏一个。模型在变强，你的技巧在变好，天花板在升高，但天花板还在。这个循环本身就是线索：问题不在可以持续优化的维度上，而在某种更根本的结构性限制上。

**注意力衰减。** 有一个现象特别能说明这种结构性。你在对话前期定下了一条架构约束："所有 API 返回值必须包含 error code 字段。"Agent 照做了。对话继续推进十几轮，讨论了别的功能，生成了大量代码。到第三十轮你让它加一个新接口，error code 字段消失了。

你去翻对话，那条约束还在第五轮。Agent 没有"忘记"它，问题出在 attention 机制上。LLM 每生成一个 token 时会回顾 context 中的所有内容，但注意力不是均匀分配的。研究表明模型对开头和结尾的信息关注度较高，中间部分的召回率显著下降。随着对话变长，你的约束被夹在越来越多的代码输出和讨论之间，分到的注意力越来越少，最终低到不再影响 Agent 的输出。信息还在，但 Agent 实际上已经"看不见"了。

更隐蔽的情况是 compaction。对话足够长之后，Agent 的运行时会静默地把早期内容压缩成摘要来腾出空间。这时信息不只是被忽略，而是被直接删除了。你和 Agent 都不知道哪些内容被删了。注意力衰减是看不清，compaction 是看不见。两者叠加，长对话中的意图对齐建立在一个不断流失的基础上。

**1.5x vs 100x。** 你不是个例。大部分开发者的 Agent 体验和你一样：体感快了，综合生产力提升有限，1.5 到 2 倍。但同样的工具，少数人做到了截然不同的成绩。PingCAP 的 CTO 用 AI 重写 TiDB 的 PostgreSQL 兼容层，产出的是接近生产水平的代码。Pigsty 创始人一个人用 AI 维护着集成了 460 多个扩展的企业级 PostgreSQL 发行版，日常同时调度十个 Agent 并行推进。同样的模型，同样的工具，差距以数十倍计。差在哪？

**过渡。** 行业开始用一个词来描述这个差距的解法：harness engineering。

## 为什么你需要 Harness

**Section takeaway: 五个结构性特征使开环控制在结构上不可行。Harness 的本质是闭环控制 + 持续演进。**

### 一个被命名但没有被解释的概念

2026 年初，HashiCorp 联合创始人 Mitchell Hashimoto 在描述自己的 AI 开发实践时最先提出了 harness engineering。他的定义是操作性的：每次 Agent 犯错，就工程化一个机制确保它不再犯同样的错。两类手段：用 AGENTS.md 引导 Agent 的行为方向，用编程化的工具让 Agent 能验证自己的产出。

几天后 OpenAI 发表了一篇更系统的文章。他们的案例很有冲击力：一个三人团队用 Codex 生成了一百万行代码，zero human-written code。他们把 harness 定义得更广：围绕 Agent 的完整系统，包括工具、脚手架、可观测性、spec 和 prompt。Martin Fowler 随后做了更正式的分析，把 harness 分解为 guides（前馈控制：引导 Agent 该怎么做）和 sensors（反馈控制：检测 Agent 做得对不对）。

这些描述在操作层面有价值。但 Fowler 自己也指出了 OpenAI 文章的一个盲区：它讨论了代码质量和可维护性，却很少谈如何验证代码是否真正满足了用户的需求。这个盲区不是 OpenAI 独有的。整个 harness engineering 的讨论都缺少一个分析基础：Agent 的什么结构性特征决定了你不能 vibe、必须 harness？

Hashimoto 说"犯了错就工程化一个修复"。这是有效的实践，但没有回答：为什么 Agent 会系统性地犯某些类型的错？OpenAI 列了一张组件清单（tools, scaffolding, observability）。这些组件各自在补偿 Agent 的什么缺陷？缺了哪个会出什么问题？没有这个分析，harness engineering 是一组操作指南，你照着做但不知道为什么，不知道什么时候够了，不知道什么时候该变通。

要回答"为什么需要 harness"，先要回答一个更基本的问题：Agent 作为执行者，跟人类到底有什么结构性差异？

### Agent 的五个结构性特征

以下五个特征来自 Agent 的技术架构。它们不是当前模型的暂时局限，而是这类系统的内在属性。理解它们，你碰到的每一面墙都能找到对应的根因。

#### 忠实执行

你觉得"AI 总是理解错需求"。更准确的描述是：Agent 忠实地执行了你给它的输入，包括输入中所有你没意识到的模糊。

LLM 的工作方式是：给定所有输入内容，逐个生成最可能的下一个 token。每生成一个 token，模型通过 attention 机制回顾所有输入，计算每个部分的相关性权重，综合这些信息做出选择。这个过程意味着输出完全由输入决定。它不会去猜你"真正想要什么"，它处理的是你实际给它的文字。

你说"加一个搜索功能"。这句话有多少没说清楚的地方？搜索范围是标题还是全文？结果按什么排序？关键词为空时怎么办？每个没说清楚的点，Agent 都按概率最高的选择填充，然后忠实执行。这些选择可能碰巧跟你的意图一致，也可能不一致，你审查产出之前无法得知。

人类程序员遇到这种模糊会调用业务常识来补全，或者直接走过来问你。Agent 不会。你的团队里有大量未文档化的隐性知识：为什么某个模块用了特定的设计模式，为什么某个 API 的错误处理有历史遗留的特殊策略，某个客户的数据格式有哪些已知异常。人类程序员通过日常协作逐步吸收这些知识。对 Agent 来说，没有写进输入的知识从未存在。产出的代码会在功能上正确地忽略这些知识。

→ 在开环控制下，你靠"说清楚"来控制输出质量。但你永远不知道自己说得够不够清楚，也不知道有多少隐性知识忘了显式提供。

#### 有限处理容量

你的直觉是"给 Agent 越多信息越好"。现实是：Agent 在单次交互中能有效处理的信息量有硬上限，而且有效容量远小于你以为的那个数字。

Agent 的全部工作记忆就是 context window。你的指令、代码文件、对话历史、工具返回的结果，所有信息拼成一个 token 序列送入模型。窗口有硬上限：当前主流模型从 128K 到 1M tokens。超出上限的内容被截断，对 Agent 完全不存在。

但硬上限不是真正的瓶颈。前面讲注意力衰减时已经展示了这个机制：LLM 的 attention 对 context 的分配不均匀，开头和结尾较高，中间部分显著下降。这意味着即使信息在窗口以内，如果被夹在大量其他内容中间，它对 Agent 决策的实际影响可能趋近于零。标称 128K tokens 的窗口，有效利用的部分可能只有一半。信息越多，每条信息分到的注意力越少，到某个点之后再加信息不是帮助而是干扰——关键约束被淹没在噪声里。

这导致两个后果。

第一，任务规模与产出质量负相关。小任务（几个文件、一个功能点）Agent 表现很好，因为所有相关信息都在有效注意力范围内。任务规模一旦超过阈值（需要同时考虑数据库 schema、API 契约、前端状态管理和权限模型），质量断崖式下降。人类程序员有对整个系统的持久心智模型，能在局部工作时维持全局一致性。Agent 必须在当前窗口内重新构建理解，装不下的部分就被忽略。

第二，长链推理中早期决策被遗忘。Agent 在一个任务中执行多步操作时（Agentic Loop：接收指令 → 推理 → 调用工具 → 观察结果 → 再推理 → 再行动），每一步的结果都追加到 context 里。早期的推理和决策逐渐被推向窗口远端，获得的注意力下降。第 5 步做出的接口设计决策，到第 50 步时可能已被有效遗忘。Agent 前半段采用的设计模式在后半段被无声地替换，它自己意识不到前后矛盾。

→ 在开环控制下，你靠"给够信息"来保证 Agent 理解全局。但给多了反而适得其反：关键信息被噪声淹没。你在"信息不足导致 Agent 不知道"和"信息过载导致 Agent 看不见"之间左右为难，没有机制知道当前处于哪种状态。

#### 无记忆积累

你昨天花了二十分钟教 Agent 项目的架构约定。它完美地执行了整个下午。今天你开一个新会话，它对昨天的一切一无所知。

Agent 的工作以会话为单位。一个会话从你发起指令开始，到任务完成或会话关闭结束。会话结束后，上下文窗口中的所有信息被清空。下一次会话从空白开始。第一百次会话和第一次会话的执行水平相同。好的决策和坏的决策以同样的概率出现。

在人类团队中，知识通过日常协作自然积累。一个人在项目上工作越久，对项目的理解越深：架构决策的历史原因、各模块的脆弱点、特定业务场景的处理惯例。这些知识大多从未被文档化，但活在团队成员的脑子里，通过 code review、站会、午餐闲聊自然传递和演化。Agent 驱动的开发缺乏这个积累过程。

更深一层的问题：即使你把知识外化为文档，文档本身也需要持续维护。人脑中的知识随项目演化自动更新，你改了架构，你脑子里的架构理解同步更新了。文档不会。项目上线了三个月，当初写的架构文档可能已经跟实际代码对不上了。不维护的文档不是中性的，它是误导性的信息源。知识外化只解决了问题的一半，知识的演进机制才是完整的解法。

→ 在开环控制下，你靠"每次重新教"来维持执行水平。项目小的时候勉强可行。项目大了之后，需要重新教的背景知识超过了你的带宽，也超过了 Agent 的 context 容量。

#### 无后果感知

你注意到代码库的整体质量在持续下降，但每个单次 PR 看起来都是合理的。没有哪个提交明显是"坏"的，但三个月后你回头看，代码库已经面目全非。

Agent 优化的是当前指令的满足度。你让它加一个功能，它加了。你没让它重构，它不会重构。它对代码的长期可维护性、技术债的积累、架构的一致性没有内在关注。人类程序员有"三个月后要维护这段代码"的预期，会为了长期可读性牺牲短期效率。Agent 缺乏这种内在驱动。

这个特征的后果是一个自强化循环。Agent 忠实复制代码库中已有的模式，包括坏的模式。你之前某次赶工留下的一段 workaround，在 Agent 看来是"项目中已有的实现模式"，会被忠实地复制到新的代码中。合并后的代码成为后续生成的参考集，坏模式不断被复制和放大。人类团队年度级别积累的技术债，Agent 驱动的团队可能在数周内达到同等规模。系统中没有任何内在力量推动重构，等你意识到需要重构时，规模可能已经使重构成本极高。

另一个后果是 Agent 不区分风险等级。修改一段展示页面的文案和修改支付扣款的核心逻辑，在 Agent 的执行层面完全一样：读指令，改代码，提交。人类面对高风险操作会本能地放慢节奏、增加确认步骤、找同事 double check。Agent 没有这种内在的风险减速机制。

→ 在开环控制下，你靠人工 review 来守住代码质量和风险控制。这是开环的最后一道防线。

#### 高吞吐零边际成本（放大器）

前四个特征在人类执行速度下都是可管理的问题。你来得及 review 每个 PR，来得及在新会话开始时重新教一遍关键约定，来得及发现一个模糊规约产出了偏离预期的实现。人类的产出速度本身就是一种错误遏制机制：产出得慢，偏差积累得慢，你有时间发现和纠正。

Agent 的产出速度是人类的 10 到 100 倍。而且可以同时实例化多个 Agent 并行工作，增加一个实例的边际成本趋近于零。启动第二个、第十个、第一百个 Agent 实例不需要招聘、培训或沟通协调。

这个特征在五个中扮演特殊角色：它不产生新的问题类型，但把前四个问题的影响放大一到两个数量级。

一个模糊的规约在人类执行时产出两三个需要修正的偏差，你来得及逐个纠正。在 Agent 执行时，同一个模糊可能在一个小时内产出几十个偏差各异的实现。无记忆在每天两三个会话时是小不便，在每天几十个会话时是严重的知识断裂。无后果感知在人类产出速度下积累技术债需要几个月，百倍速下几周就到同等规模。

人类的慢速产出为所有下游活动提供了天然的时间缓冲。代码审查、架构评估、集成测试的节奏与人类产出速度匹配。百倍速打破了这个匹配。审查从逐行 review 退化为抽样检查。偏差在被人类发现之前已经被后续几十次提交固化为"项目中已有的模式"。

你的最后一道防线——人工 review——在百倍产出面前彻底失守。你不可能以百倍速度审查百倍产出。开环控制不是效率低的问题，是结构上不可行。

### Harness 的本质：闭环控制

五个特征的共同指向是一件事：你需要外部的、自动化的、独立于 Agent 的反馈机制。

Vibe coding 是开环控制：发出指令，接受结果，凭感觉判断好坏。开环在小规模、低速度下可以凑合。当执行者忠实于输入（你说不清它就随机选）、处理容量有限（给多了反而坏事）、没有记忆（每次从零开始）、没有后果感知（不会自我纠正）、而且以百倍速度运行时，开环的失败是确定性的。

闭环控制做两件事。第一，规约定义"对"是什么。不是"加一个搜索功能"这种模糊描述，而是一份 Agent 可以对照执行的操作定义，包含意图（做什么、为什么）、验收条件（怎么算做对了）和约束（不该动什么）。规约对应的是忠实执行特征：既然 Agent 忠实于输入，就让输入足够精确。第二，验证检查"做对没有"。不是你肉眼看，不是让 Agent 自己测自己，而是独立于 Agent 的、自动化的、可重复的检查机制。验证对应的是无后果感知和有限处理容量：Agent 不会自我纠正，而且会在长链推理中偏离，你需要外部力量在偏差发生时及时拉回。规约和验证构成反馈回路：偏差被即时发现并纠正，而不是在最终交付时才暴露。

闭环解决了单次执行的可靠性。但系统还需要第二个原则：持续演进。规约会过时，测试会腐烂，流程会僵化。无记忆特征意味着知识不会自动更新，无后果感知意味着退化不会被内在力量阻止。如果没有显式的演进机制，系统会自我强化地滑向退化。演进不是可选的改进步骤，是 harness 的组成部分。

闭环控制加持续演进，这是 harness engineering 的完整定义。不是一份 AGENTS.md，不是一套工具集，是一个围绕 Agent 结构性特征设计的闭环控制体系。

回到 Hashimoto、OpenAI 和 Fowler 的描述：AGENTS.md 是规约的一种形式，验证工具是闭环的一个组件，Fowler 的 guides/sensors 分解是闭环结构的一种表达。这些实践都在做对的事。本书要做的是把它们放在一个统一的分析框架里，让你理解每个组件在补偿哪个结构性特征，判断自己的体系够不够，知道什么时候需要加强。

## 全书路线图

**Section takeaway: 三卷沿生产力阶梯展开，从你当前的阶段读起。**

全书按生产力阶梯展开，每一卷对应一个跃迁阶段。

**卷一：可靠的 Agent 编程。** 建立闭环。规约章节讲怎么把模糊的意图变成 Agent 能精确执行的输入（对应忠实执行）。验证章节讲怎么用自动化手段证明产出是对的（对应无后果感知和有限处理容量）。你坐在 Agent 前面一问一答，但产出从碰运气变成工程化交付。

**卷二：规模化 Agent 开发。** 在闭环基础上放手。没有卷一的规约和验证，自主执行就是 YOLO mode。第四章处理长期执行中的上下文管理和跨会话记忆（对应有限处理容量和无记忆）。第五章扩展到多 Agent 并行，解决隔离与集成（利用高吞吐的优势，同时管理它的风险）。你从操作者变成任务的设计者和验收者。

**卷三：治理百倍速的组织。** 个人效率不再是瓶颈后，瓶颈转移到团队层面。分工、流程、角色定义都是为人类速度设计的，需要重新匹配 Agent 时代的节奏。卷一卷二的工程实践（规约、验证、分解、平台）是组织级协作的基础设施。

三类读者可以从不同入口开始。如果你是工程师，正在从"自己写代码"转向"指挥 Agent 写代码"，从卷一开始。如果你是产品人或编程新手，已经用 vibe coding 做出了能跑的产品，卷一的规约和验证会直接帮到你。如果你是技术负责人，正在推动团队 AI 转型，可以先看卷三理解组织层面的挑战，再回到卷一卷二了解工程基础。
