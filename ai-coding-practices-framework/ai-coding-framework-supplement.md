## 一、质量控制的深化讨论

### 1. 质量的多层次问题（2026-03-05）

**关键发现**：质量不只是"代码能跑"，有多个层次

**马工的分层**：
1. **代码质量** - 能否运行、有无bug
2. **算法/业务质量** - 效果是否达标（例：电商推荐系统延迟低但推荐效果差）
3. **交付时间** - 交付速度本身也是服务质量的一部分

**痛点**：越上层越难测试和评估

**解决思路**：
- 先建立 benchmark（哪怕粗糙）
- 通过"修 bug → benchmark 上升 → 快速迭代"的反馈环不断改进
- 关键词是"不断提升"：代码和 benchmark 都不断提升

**实践案例**：
- 马工的分类程序没有 ground truth，难以评估
- 建立 benchmark 后，修一个 bug，分数上升 3 分
- 有了快速反馈环，可以放心大胆快速迭代

### 2. Code Review 已死 - 用什么替代？（2026-03-04）

**核心矛盾**：
- 传统：代码写和审的效率差不多，不会产生瓶颈
- AI 时代：AI 生成速度是人的几千上万倍，人工审核完全失效

**争议焦点**：

**冯骐的观点**：
- "code 的 review 这么多年了，人拉的屎一点都没少"
- 没有证据证明人的 code review 质量比 AI 的 code review 质量高
- 现在只做每个 phase 的端到端集成测试

**刘连响的反驳**：
- 公司级对稳定性要求很高的项目还是要 review
- 能 review 出来很多问题
- 功能正常，但对后续持续运营带来风险（测试难以发现）

**陈浩的分类**：
Code review 能找出的问题：
1. 开发规范类
2. 技术方案类
3. 功能测试不容易发现，但 review 能注意到的 bug

**DieselNiu 的视角**：
- Code review 主要是 sharing，不是看谁写得差
- 如果结对编程 + 频繁 switch，根本不需要 code review

**未解决的问题**：
- 如何用自动化机制替代 code review 的"分享知识"功能？
- 如何捕获"功能正常但运营风险高"的问题？

### 3. 组织级质量控制的挑战（2026-03-07）

**ROARRR 的实践痛点**（70 人研发团队 + 数百非技术人员）：

**规模化后的新问题**：
- 项目大了，作者很多，如何保障各种文档之间的一致性？
- md/skill 达到一定规模后：
  - 如何增加知识密集度？
  - 如何有效索引？
  - 如何分层？

**马工的回应**：
- 这是一系列待组织的话题
- 显然不只是"用 md 文件和 skill，加统一模型"这么简单

## 二、瓶颈转移的系统分析

### 约束理论视角（2026-01-22，李峻）

**核心观点**：
- 一个系统的产出速度取决于其最慢的环节（瓶颈）
- Coding 曾是瓶颈，AI 把它拓宽了
- **瓶颈迅速转移到**：Code Review、QA、Deployment、Communication

**关键结论**：
在这些新瓶颈被解决之前，系统的整体产出（Throughput）不会有任何提升

**委托代理问题**：
- 研发（代理人）与公司/PM（委托人）利益不一致
- 缺乏激励机制变革（如：提效不裁员、提效涨薪）
- 研发人员理性的最优解：**"维持现状，享受 AI 带来的摸鱼时间"**

**外包不出去的环节**：
- 设计和需求抽象
- 决策和抽象思维的过程
- "说都说不清晰"是最大障碍

## 三、Skill 体系的深化

### 1. Skill 验收标准缺失（2026-03-05）

**马工提出的核心问题**：
一个 skill 满足什么条件，才能算合格的？

**当前现状**：
- 大多数人：满足要求即可，一直迭代
- 薇冷 Violet：靠不断迭代，用了发现问题就沉淀踩坑，更新 skill
- 海生：参考论文中的绩效管理指标（如游戏策划的 skill）

**暴露的问题**：
1. **更新导致内容重复**（duplication）
2. **不同 skills 没有正交性**，互相踩脚
3. **从别人那里 clone 来的 skill 因配置问题无法运行**

**Silicon 大康的提议**：
- 传统代码有 CI/CD
- Skill 上传后能否也有 CI/CD 流程？
- 拉到 Agent 沙盒里跑测试

**马工的回应**：
- **"先有个标准，才能跑验收流程"**
- 现在大家也没个标准
- "我要给我所有的 skill 发牌照，禁止无证上岗"

**Booker Zhao 的朴素标准**：
- 简洁
- 正交
- 面向场景
- 异常处理流程

### 2. Skill 体系接近产品级 Coding Agent（2026-02-11，胥克谦）

**成果**：
- 从零需求到完整文档 + 代码：2-3 天 → 0.5 天
- 多阶段滚动执行、中断可续跑、自动上下文清理
- "无限接近于产品化"

**核心方法论**：

**1) 文档驱动 > 提示词驱动**
- "提示词应该算是古法 AI 编程了"
- 每个 skill 都有 3000+ 行（PRD + 架构文档）
- 信息量大，质量可控

**2) PRD skill 包含多轮动态interrogation**
- 动态评估是否获得足够信息
- 而非机械地问 N 个问题

**3) 原子颗粒度执行 + 测试 + 滚动执行**
- 王欢.ai 提出的痛点：每个环节信息都会丢（User story → 设计 → 模块 → UI）
- 胥克谦的答案：原子颗粒度做执行与测试，滚动执行

**4) 经济性**
- Codex：1.5B tokens/天 ≈ 250 RMB（一个清洁工的日薪）
- 产出：500-800 人年的等效产出
- 一年 10 万块

### 3. Skill = 编排 + 具体动作（Silicon 大康）

**观察**：
- 如果采用纯智能体驱动的后端，所有工作其实是"捏 Skill"
- Skill 套 Skill：编排可以是 skill，具体动作也可以是 skill

**分层结构**（对应原始框架）：
- 共享 Skill
- Meta Skill（编排和管理其他 Skill）
- 领域 Skill

## 四、Harness Engineering（驾驭工程）

### 概念（2026-03-09，issue）

**定义**：
谁把仓库、流程、运行时、观测、规则和反馈回路，做成了一个**适合智能体稳定工作的 harness**？

**核心组件**：
1. **仓库知识结构** - Repository knowledge structure
2. **可执行计划** - Executable plans
3. **自动化验证** - Automated verification
4. **机器可读的 UI 与可观测性** - Machine-readable UI & observability
5. **强架构边界** - Strong architecture boundaries
6. **自动 review** - Auto review
7. **技术债垃圾回收** - Tech debt garbage collection

**关键概念**：**验证债务**（Verification Debt）

**参考实现**：
- Phodal 的 Routa 项目：https://github.com/phodal/routa
- "照着抄就好了"

## 五、信任边界与 Agent 权限悖论

### Agent 权限与质量控制的悖论（2026-02-26）

**艺玲提出的核心困境**：
- **权限大了**：Agent 容易搞崩系统
- **权限小了**：无法完成真正的自主任务

**真实案例**：
- 锅：让小龙虾迁移 3 个文件，搞了半小时，最后把文件全删了
- 金松：每两天系统崩一次
- 吴昊 Cubic：本地部署会自己把配置搞崩

**本质问题**：
- 表面上看是工具不稳定
- **实际上**：AI 当前的工作模式还不适合无人值守系统

**两个解决方向**：

**1) 架构层面**：
- 沙箱
- 权限隔离
- 回滚机制
- 而不是指望 AI "聪明"

**2) 任务分解**：
- 崔富泽：胥老师能持续通过文档驱动长期编程，是因为把任务文档全都弄好了
- 不是工具问题，是使用者的问题

## 六、关键洞察总结

### 1. 质量控制的三个层次
- 代码质量（能跑）
- 业务质量（效果好）
- 交付速度（快）

### 2. Benchmark 先行
- 没有 ground truth 不要紧
- 先建立粗糙的 benchmark
- 建立快速反馈环

### 3. 瓶颈已转移
- 不再是写代码
- 而是 Review、QA、Deployment、Communication

### 4. Skill 标准化是组织能力的关键
- 当前缺乏验收标准
- 需要类似 CI/CD 的验证流程
- 简洁、正交、面向场景、异常处理

### 5. Harness Engineering 是基础设施
- 不只是写 AI 工具
- 而是建立**适合 AI 稳定工作的环境**
- 包括：知识结构、验证、边界、反馈回路

### 6. Code Review 的替代方案未确定
- 传统 review 已失效
- 但自动化方案还不完善
- 特别是"运营风险"和"知识分享"功能

### 7. Agent 权限悖论需要架构解决
- 不能指望 AI 自己小心
- 必须通过沙箱、隔离、回滚等机制

### 8. 委托代理问题是组织挑战
- 技术问题可以解决
- 激励机制不变，提效就会变成摸鱼
