## 补充问题 #6（产品经理视角的技术把控）

我继续提一些小白问题啊：

1. 对于产品经理，对技术架构不熟，CC，CODEX这类推荐的技术架构普遍不新，在企业里面应用的花，很容易导致可能后续上线验收或者移交给安全部门和运维部门的时候，就发现版本过低，高危安全漏洞多，那个时候再来各种打补丁，那将导致很多原来的接口，调用方式大改，返工难度大，甚至说无法再实现。这个怎么破？因为产品经理是肯定没有技术架构把控力的。

2. 棕地项目怎么避免在修改和补充新功能时，CC和CODEX不去修改其他功能？因为在LOOP，长时间执行过程中，人是不看，甚至没法看的情况下，怎么能保证不走偏，或者能发现它走偏？

3. 大模型很多时候喜欢偷懒，说因时间限制和TOKEN限制从而简化执行，同样的，如何不简化而精准实现，或者及时能发现它偷懒

4. 怎么长时间让大模型自动执行开发，HUMEN 不在这个自动化LOOP的时候，保证质量的手段是什么

5. 测试和验收时保证大模型开发质量和多次LOOP逐渐回到正确目标的重要事项，但测试架构和单测这些也是大模型写的，产品经理也看不懂，那么如何保证大模型写测试相关内容的时候不是自欺欺人？同样大模型在自身发现BUG，修改BUG，然后测试的过程中，很多时候，跑了几次就去改测试方式了，怎么避免，上次听到老师说，写MOCK SERVER，希望分享和演示如何快速写MOCK SERVER

6. 自动化测试主要用什么工具，playwright-cli？有什么坑吗？

7. 自动化测试很多时候是功能测试，但系统很多时候是要对外服务的，压力测试怎么自动化做？也是用JMETER这些吗？有什么建议和经验
